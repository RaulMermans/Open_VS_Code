# ADR-018: Chat UI and Agent Context Execution

## Status
Accepted (Sprint 3B.3)

## Context
The IDE chat extension needs to communicate with the Agent core robustly without duplicating business logic, maintaining security around file mutations, and accurately rendering history and status states in real-time.

## Decisions

### 1. ContextCompiler Authority
The `ContextCompiler` is the absolute authority on agent context. The Chat UI never builds or summarizes context. It solely displays the ongoing `ConversationTurn` history that was computed and managed by the core.

### 2. Structured recentTurns
Chat history sent back to the Agent core is passed using a strict `ConversationTurn[]` structure (defined in `contracts/context.ts`) instead of loosely typed strings or generic any arrays. This prevents parsing desync and guarantees the model provider gets exactly the turns the user sees.

### 3. Exact Confirmation ID Matching
Mutations requests emit a `mutation.requested` event containing the tool invocation. The Chat UI tracks this with a generated Confirmation ID. When the user clicks "Approve" or "Reject", this exact Confirmation ID must be sent back to `AgentSessionBridge` via `requestConfirmation` to ensure the correct pause lock is resolved.

### 4. Cancel-During-Confirmation Semantics
If the user cancels the chat turn while the system is blocking on a pending confirmation (e.g. they click "Cancel" instead of "Approve/Reject" for a tool), the `AgentSessionBridge` immediately aborts the active runner lock, rejects the pending mutation automatically, and prevents the tool execution. The Chat UI must handle this seamlessly.

### 5. Presentation Layer Only
The Chat UI (`ChatController` and webview) is strictly a presentation layer. It does not evaluate tool schemas, determine if a task is "safe", or inspect LLM outputs. It listens to event streams (`model.requested`, `task.started`, `mutation.requested`) and renders state accordingly.

## Consequences
- Testing can accurately simulate UI races and backend delays because the backend does all the actual work, allowing true E2E headless validation.
- All "stale turn" bugs are solved by the strict `activeTurn` check against `currentConversationId` discarding orphaned callbacks.
- File writes are fully blocked until the precise `confirmation.respond` ID clears the await lock in `IdeHost`.
