# ADR-017: IDE Host Adapter Boundary

**Date**: 2026-09-06
**Status**: Accepted

## Context

Sprint 3A begins the IDE product layer. The core `agent-core` package is editor-independent and fully proven, including routing, project memory, skills, MCP, mutations, and repair orchestration.

We must connect this core to VS Code/Code-OSS without duplicating any reasoning, permissions, execution loops, or configuration. We also want to guarantee that `agent-core` does not adopt a hard dependency on the `vscode` module or its lifecycle.

## Decision

We introduce an IDE-neutral adapter contract (`IdeHost` and `IdeContextSnapshot`) and a production integration component (`AgentSessionBridge`) inside a new `@open-vs-code/ide-adapter` package. 
We provide a minimal VS Code extension in `@open-vs-code/vscode-integration` that implements `IdeHost` and maps basic VS Code concepts (active file, selection, diagnostics) into bounded snapshot DTOs.

- **IDE host != agent core**: The IDE is merely a host. It provides ephemeral context (editor state) and a visual output channel. It does not control agent permissions or execution loops.
- **Zero `vscode` dependency in agent-core**: The core remains completely independent of VS Code or any IDE-specific typing.
- **Adapter Contracts**: The host is accessed via a slim `IdeHost` interface containing deterministic, non-leaky APIs (e.g., bounded diagnostics, max 20 visible files, 50,000 char selection bounds).
- **Ephemeral IDE Context**: Context sent to the model (selection, active file) reflects the ephemeral buffer state. It is injected transiently and not persisted as durable project memory.
- **Existing Subsystems Retained**: The bridge delegates perfectly to the existing `AgentRunner`, `ProjectMemoryLoader`, `ContextCompiler`, `MutationEngine`, `RepairOrchestrator`, etc. No parallel implementations exist.
- **Confirmation Bridge Only Renders Requests**: The IDE host merely renders a Yes/No modal when the core `MutationEngine` pauses execution for human approval. The IDE does not decide what is safe.
- **Exact Approval Binding**: When a mutation is approved, the IDE returns `APPROVE` or `REJECT` directly bound to the exact payload generated by the core.
- **Cancellation Propagation**: VS Code's `CancellationToken` is mapped to an `AbortSignal` and given to the `AgentRunner`, which propagates it deterministically to all providers and tools.
- **Workspace Trust**: `vscode.workspace.isTrusted` is passed to the bridge. If the workspace is untrusted, the bridge immediately rejects `BUILD` or `DEBUG` requests before they reach the core. It delegates safely-isolated `ASK` mode if appropriate.
- **Dirty-buffer Limitation**: We expose `isDirty` and document that the agent's file tools still read from the actual filesystem (disk), not the virtual editor buffer.
- **Zero Autonomous Model Calls**: Extension activation, file selection, and editor changes trigger absolutely zero model calls. Only explicit command invocation (`open-vs-code.ask`, etc.) starts a session.
- **Deferred UX**: We intentionally use minimal primitives (`showInputBox`, `OutputChannel`, `showWarningMessage`) rather than building chat views or diff views, which are explicitly deferred to Sprints 3B, 3C, and 3D.

## Consequences

- The `ide-adapter` package provides a unified layer we can test with a purely deterministic `TestIdeHost` matrix. We do not require an Electron test runner to verify IDE orchestration behavior.
- Real VS Code integration is small, stateless, and mostly plumbing.
- We maintain perfect feature parity and identical behavioral boundaries across the CLI and VS Code extension because they share the same backend runner setup.
