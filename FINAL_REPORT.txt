2. INVARIANTS & GUARANTEES SEALED
--------------------------------------------------------------------------------
1. Write-Ahead Durability Gate:
   No filesystem mutation, external process execution, rollback write, or session resume
   is permitted to execute unless its intent is durably committed to the append-only
   `OperationJournal` and validated by a checkpoint.
2. Truthful Observed State Reconciliation:
   Filesystem ground truth (SHA-256 hash match against expected postcondition or
   precondition) dictates operation status (`RECONCILED_APPLIED` or `RECONCILED_NOT_APPLIED`).
   Ambiguous or altered states trigger `BLOCKED_DIVERGENCE` and `ASK_HUMAN`.
3. Fail-Closed Error Confinement:
   Any durability persistence failure (`DURABILITY_UNAVAILABLE` or `RECOVERY_PERSISTENCE_FAILED`)
   halts execution immediately with `failureReason: "INTERNAL_ERROR"`, emitting
   terminal lifecycle events and prohibiting further mutations or model inference.
4. Sole Write Authority:
   `RecoveryController` and `RollbackManager` never perform ad-hoc filesystem writes;
   all file modifications route through `MutationEngine` under path-containment boundaries.
5. Verification Durability & Integrity:
   Verifications follow `BEFORE_VERIFICATION -> STARTED -> VerificationEngine -> COMPLETED -> AFTER_VERIFICATION`.
   Completed verifications remain `COMPLETED` across restarts; interrupted ones yield `REVERIFY`.
6. Stale Epoch Invalidation:
   Approvals and tokens from prior process epochs are strictly invalidated across restarts
   (`NEW_EPOCH_AUTHORITY_REQUIRED`), preventing replay attacks.

3. EXACT PRODUCTION Gaps CLOSED
--------------------------------------------------------------------------------
- Gap 1: `resumeFromRecovery()` previously lacked an explicit catch block around
  persisting `RECOVERY_RECONCILED`, risking partial resumption on disk errors.
  -> CLOSED: Wrapped with try/catch; emits `task.failed`, sets `INTERNAL_ERROR`,
     and returns immediately with 0 model/tool invocations.
- Gap 2: In `executePendingApproval`, `executeTool`, and verification runs, if execution
  failed and `recordFailed()` persistence also failed, the runner could fail open or
  attempt downstream steps.
  -> CLOSED: Enforced immediate fail-closed check emitting `RECOVERY_PERSISTENCE_FAILED`
     and halting the session.
- Gap 3: Rollback executed reverse mutations directly without write-ahead journaling
  of the rollback operation itself.
  -> CLOSED: Rollback now writes `ROLLBACK_MUTATION` with `recordPrepared` and `recordStarted`

- Gap 4: Duplicate rollback attempts could re-apply patches if the journal did not record
  the rollback operation ID.
  -> CLOSED: Added duplicate rollback detection that checks if disk is already restored,
     returning `ROLLED_BACK` with 0 reverse writes, or `DIVERGED` if disk altered.
- Gap 5: Rollback process crashes were not verified end-to-end across child process exits.
  -> CLOSED: Real child-process crash tests `T-5114` - `T-5117` in `crash-process-e2e.test.ts`.

  -> CLOSED: Real `AgentRunner` verification durability tests `T-5119` - `T-5120` proving

  explicitly proven to block engine execution.
  -> CLOSED: Added deterministic tests `T-5121`, `T-5122`, and `T-5123`.

4. COMPLETE WRITE-AHEAD LIFECYCLE CONTRACTS
--------------------------------------------------------------------------------
Every stateful operation adheres to this immutable lifecycle:

Mutation Lifecycle:
1. Intent: `preparePatch` / `prepareCreate` produces `PreparedMutation`
2. Prepare: `coord.prepareOperation({ kind: "MUTATION", ... })` -> `recordPrepared`
3. Gate 1: Checkpoint `BEFORE_MUTATION` (persistence failure -> FAIL CLOSED)
4. Start: `coord.operationJournal.recordStarted(opId)` (persistence failure -> FAIL CLOSED)
5. Authority Execution: `MutationEngine.applyPreparedMutation` (sole write authority)
6. Outcome:
   - Success: `coord.operationJournal.recordCompleted(opId)`
   - Failure: `coord.operationJournal.recordFailed(opId)` (persistence failure -> FAIL CLOSED)
7. Gate 2: Checkpoint `AFTER_MUTATION` (persistence failure -> FAIL CLOSED)

Verification Lifecycle:
1. Intent: `prepareForReview` / `discoverVerificationCommand` produces `PreparedVerification`
2. Prepare: `coord.prepareOperation({ kind: "VERIFICATION", ... })` -> `recordPrepared`
3. Start: `coord.operationJournal.recordStarted(opId)` (persistence failure -> FAIL CLOSED)
4. Gate 1: Checkpoint `BEFORE_VERIFICATION` (persistence failure -> FAIL CLOSED)
5. Authority Execution: `VerificationEngine.execute`
6. Outcome:
   - Pass: `coord.operationJournal.recordCompleted(opId)`
   - Fail: `coord.operationJournal.recordFailed(opId)` (persistence failure -> FAIL CLOSED)
7. Gate 2: Checkpoint `AFTER_VERIFICATION` (persistence failure -> FAIL CLOSED)

Rollback Lifecycle:
1. Assessment: `assessRollbackCandidates` evaluates preconditions and preimage
2. Gate 1: Double-check disk state (if already restored -> suppress with 0 writes; if modified -> DIVERGED)
3. Prepare: `coord.prepareOperation({ kind: "ROLLBACK_MUTATION", ... })` -> `recordPrepared`
4. Start: `coord.operationJournal.recordStarted(rollbackOpId)` (persistence failure -> FAIL CLOSED)
5. Authority Execution: `MutationEngine.rollback` / `applyPreparedMutation`
6. Outcome:
   - Success: `coord.operationJournal.recordCompleted(rollbackOpId)`
   - Failure: `coord.operationJournal.recordFailed(rollbackOpId)`
7. Gate 2: Checkpoint `ROLLBACK_COMPLETED`

5. FAIL-CLOSED DURABILITY GATE ARCHITECTURE
--------------------------------------------------------------------------------
All durability gates in `AgentRunner` follow strict fail-closed semantics:
- Persistence errors throw `DURABILITY_UNAVAILABLE` or trigger `RECOVERY_PERSISTENCE_FAILED`.
- The session transitions to `FAILED` with `failureReason: "INTERNAL_ERROR"`.
- Events emitted: `task.failed` with explicit diagnostic message.
- Zero subsequent turns, zero model API requests, zero tool invocations.
- Handled at:
  - Initial `RUN_STARTED` checkpoint
  - Pre-mutation `prepareOperation` & `BEFORE_MUTATION` checkpoint
  - Pre-verification `prepareOperation` & `recordStarted`
  - Post-mutation/post-verification `recordCompleted` / `recordFailed`
  - Post-mutation `AFTER_MUTATION` & post-verification `AFTER_VERIFICATION`
  - Recovery reconciliation `RECOVERY_RECONCILED` checkpoint
  - Final task `COMPLETED` checkpoint

6. ROLLBACK AS FIRST-CLASS JOURNALED OPERATION
--------------------------------------------------------------------------------
In `contracts.ts`:
- `"ROLLBACK_MUTATION"` added to `OPERATION_KINDS`.
- `rollbackOperationsRecovered` and `rollbackDuplicateWritesPrevented` added to metrics.

In `rollback.ts`:
- Accepts optional `OperationJournal` and `CheckpointStore`.
- Computes deterministic idempotency keys via `computeOperationIdempotencyKey`.
- Writes write-ahead journal entry before modifying workspace.
- Detects if disk is already in restored preimage state and suppresses duplicate writes.
- Detects post-mutation modifications and aborts with `DIVERGED`.
- Records completed/failed outcome and emits `ROLLBACK_COMPLETED` checkpoint.

In `reconciliation.ts` & `recovery-controller.ts`:
- Routes `ROLLBACK_MUTATION` to `reconcileMutation` for truthful hash verification.
- Reconciles to `RECONCILED_APPLIED` without replay if disk matches preimage.
- Filters rollback candidates strictly to forward `MUTATION` operations.

  3. Process A is terminated with `process.exit(1)` BEFORE the reverse write occurs.
  4. Process B recovers: inspects disk, observes file still in forward mutated state,
     reconciles `ROLLBACK_MUTATION` to `RECONCILED_NOT_APPLIED` without automatic replay.

22. PROCESS EPOCH INVALIDATION & REPLAY DEFENSE
--------------------------------------------------------------------------------
- `processEpochId` is generated per Node process instantiation using `crypto.randomUUID()`.
- On restart, any checkpoint from a previous epoch has its approvals invalidated.
- Disposition `RECONFIRM` with `NEW_EPOCH_AUTHORITY_REQUIRED` prevents automated replay.

--------------------------------------------------------------------------------
23. VERIFICATION DISCOVERY & STALE DETECTION
--------------------------------------------------------------------------------
- `discoverVerificationCommand` parses `package.json` and hashes script body.
- `VerificationEngine` verifies that `package.json` has not been tampered with since preparation.
- If hash mismatches or script altered, execution is rejected with `STALE_VERIFICATION`.
- Consumed verification execution IDs cannot be re-executed (`EXECUTION_ERROR`).
